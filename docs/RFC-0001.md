# RFC-0001: Verified Evolution Protocol (VEP) 0.3.0

Status: Draft, reference MVP. License: Apache-2.0. Key words MUST/SHOULD follow RFC 2119.

## 1. Purpose
VEP is a source-control-independent protocol in which software changes are *proposals* and *verified improvements* are the output. Lifecycle:

OBJECTIVE → AUTHORITATIVE SNAPSHOT → CANDIDATE → POLICY VALIDATION → RESOURCE AUTHORIZATION → EXECUTION → INDEPENDENT EVIDENCE → EXACT-SNAPSHOT CERTIFICATION → VERIFIED IMPROVEMENT.

Goal: minimize total expected resource per correctly verified improvement, subject to immutable correctness, security, authorization and reliability constraints. Git compatibility is read-only inspection.

## 2. Serialization (VEP-C1)
Values: null, bool, integers |n|<2^63, strings, arrays, objects with string keys. Floats, NaN, Infinity are forbidden; decimals are strings. Canonical form: UTF-8, keys sorted by code point, separators `,` `:`, no whitespace, no ASCII escaping. Parsers MUST reject duplicate keys and non-canonical object bytes.

## 3. Identity
`id = <prefix>-<hex SHA-256( "vep-id\0" ‖ len4(domain) ‖ domain ‖ len8(fields) ‖ fields )>` with `domain = "vep.<Type>.v<schema_version>"` and `fields` the canonical bytes of the fields map. Prefixes: obj snap claim cand act evd cert obs rcpt lease ctx pol exp. Object envelope: `{"type","schema_version","fields"}`; unknown fields and versions are rejected.

## 4. Objects
Objective, Snapshot, WorkClaim, Candidate, Action, Evidence, Certificate, Observation, TokenReceipt, BudgetLease, ContextManifest, ExecutionPolicy, OptimizationExperiment. Field lists are normative in `src/vep/objects.py` (SPECS) and rendered in `docs/VARIABLES.md`. Mutable state (candidate status, reservations) lives outside objects.

## 5. Storage
A CAS maps SHA-256(bytes) → bytes with atomic writes and verify-on-read. An object index maps object ids to CAS digests; ids are always re-derived from content.

## 6. Snapshots
Manifest v1: sorted list of `{path, digest, type:"file", executable}`. Paths are relative, `/`-separated, without `.`/`..`/empty components. Symlinks and special files are rejected; case/Unicode-normalization collisions are rejected; VEP state and credential-like names are excluded.

## 7. Policy and evaluator grammar
An ExecutionPolicy (frozen by id) names an evaluator from a closed grammar (`unittest`, `pytest`; structured fields only), protected glob patterns, required test files by digest, limits and audits. A candidate MUST NOT add, modify or remove protected paths, MUST retain every required test unchanged, and MUST NOT add modules named like standard-library or runner modules at an import root.

## 8. Candidate state machine
PROPOSED → POLICY_CHECKED → BUDGET_RESERVED → EVALUATING → EVIDENCE_READY → CERTIFIED; any non-terminal state → REJECTED. Transitions use compare-and-swap on a version counter and append to an immutable log. EVIDENCE_READY and CERTIFIED MUST NOT be reachable without PASS evidence / a certificate bound to the candidate's snapshot (enforced by storage-level triggers).

## 9. Resource authorization
Budgets form a hierarchy (organization, project, objective, candidate, operation) in integer micro-USD. `reserve` MUST verify every ancestor atomically. `settle` is idempotent per settle key; actual spend above the hold is recorded as overrun; open reservations whose outcome is unknown are UNCERTAIN and keep funds held. Execution MUST NOT start without a successful reservation.

## 10. Execution and evidence
Pre-execution checks, in order: candidate identity; snapshot integrity; policy identity; evaluator grammar; required tests; authorization; budget; staging boundary. Execution stages the exact snapshot read-only outside the workspace and runs the protected runner with a scrubbed environment. Post-execution: the report MUST establish discovery and execution (≥ `min_tests` passed, not all skipped, every required test file executed, internally consistent, exit status consistent) and the staged tree and signing key MUST be unchanged. Only then is Evidence signed. Failing-but-valid runs produce signed FAIL evidence and REJECT the candidate. Non-isolated execution MUST require explicit authorization and MUST be labeled `NONE_TRUSTED_LOCAL`.

## 11. Signing
Envelope `{payloadType, payload(base64), signatures[1]{keyid, sig}}`; signature is Ed25519 over DSSE PAE(payloadType, payload). Verifiers resolve `keyid` in a local trusted-key registry (SHA-256 of raw public key) and MUST reject unknown or revoked keys.

## 12. Certification and verification
A Certificate binds candidate, objective, snapshot, policy, evidence id and evidence envelope digest, and is signed. Verification MUST: verify both signatures; check all bindings; check the evidence is PASS and produced from the certified snapshot; and, in current-source mode, hash the live tree and require equality with the certified snapshot. Certificates MUST NOT be inherited by modified sources, compositions, or different objectives/policies.

## 13. Routing, caching, context (advisory computations)
Offline, deterministic, no model calls. Routing selects the lowest expected-cost eligible policy given supplied, labeled estimates; cascades require a measured false-accept bound. Cache planning gives break-even economics only. Context manifests are lossless, budgeted, and never truncate protected requirements.

## 14. Isolation
Optional adapter targeting Docker+gVisor: digest-pinned local image, no network, read-only source mount and root filesystem, dropped capabilities, no-new-privileges, non-root, CPU/memory/PID limits, tmpfs. Missing runtime ⇒ `ISOLATION_UNVERIFIED`; implementations MUST NOT fall back to host execution.
