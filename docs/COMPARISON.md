# Comparison

VEP complements these tools; it does not replace any of them. Descriptions of other projects are deliberately general; consult their own documentation (links below) for specifics. Numbers are VEP measurements on one machine under background load ([BENCHMARK_METHODOLOGY.md](BENCHMARK_METHODOLOGY.md), deviations section).

| | What it is for | What VEP adds on top | What VEP lacks compared with it |
|---|---|---|---|
| **Git** ([git-scm.com](https://git-scm.com/)) | Versioning and merging source | Binds a verification result to a content-addressed snapshot, records the Git commit and dirty state read-only; composes candidates with a three-way merge and says a textually clean merge still needs evaluation | VEP never commits, branches or pushes; it is not a version-control system |
| **GitHub Actions** ([docs](https://docs.github.com/en/actions)) | Running workflows on repository events | A portable certificate/bundle checkable offline; frozen required tests; trust labels. VEP runs *inside* Actions: the isolation workflow in this repository does exactly that ([isolation results](isolation/README.md)) | Hosting, scheduling, secrets management, a UI, the whole ecosystem |
| **Bazel and the Remote Execution API** ([remote-apis](https://github.com/bazelbuild/remote-apis)) | Hermetic builds, shared caches, remote execution at scale | A change-level acceptance record around the test run | Everything on the build side: VEP has a small local content-addressed result cache for deterministic actions and **no** remote-execution support (not implemented, not tested). On a cache hit VEP skipped almost all work (99.0% [C:cache-hit] faster than a direct run), but that path yields no certificate and the first run costs about twice a direct run because determinism is checked |
| **pytest-testmon** | Change-based test selection | An exact-snapshot guarantee: VEP never skips tests for a changed tree | Speed: testmon was about 42.7x [C:testmon-rerun] faster on an unchanged re-run and about 18.2x [C:testmon-edit] faster after a small edit in the longer-suite project |
| **Agent orchestration frameworks** | Calling models, tools, multi-agent flows | A verification and accounting layer around whatever produced the change; an adapter interface and usage-provenance labels. The core never calls a model | Orchestration, prompt management, retries against a model, tool ecosystems |
| **SLSA** ([slsa.dev](https://slsa.dev/spec/v1.2/)) and **in-toto** ([in-toto.io](https://in-toto.io/)) | Build provenance and supply-chain attestations | Test-evidence certificates tied to a snapshot | VEP does not produce SLSA provenance, claims no SLSA level and is not in-toto compatible; its signed envelope is DSSE-style with its own payload type |

## Speed in one place
On the longer suite VEP cost +2.0% [C:t1-big] over a direct run for a single verification (within the pre-declared 10% band, so reported as no measurable difference); on the short suite it cost +43.8% [C:t1-small]. With four workers a batch of four candidates finished 58.8% [C:batch-par] faster than sequential direct runs, in line with plain parallel execution. VEP's controller scaled by 4.4x [C:scale8] going from one to eight workers on tiny jobs and no further at sixteen, with about 7% [C:overhead] controller overhead ([CONTROLLER_SCALING.md](CONTROLLER_SCALING.md)).
